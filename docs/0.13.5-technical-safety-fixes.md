# 0.13.5：记忆定位、发送前复核与关闭顺序

本页保留0.13.5当时的修复与“不重载／无生产实测”边界。当前0.13.6会实际重载并验收[QQ历史回放恢复](0.13.6-qq-replay-recovery.md)，不能把本页历史安排当成本轮仍不重载。

本补丁针对隔离检查中发现的三处技术问题：记忆编号碰撞时读错／误删、等待期间旧发送任务使用过期连接与权限、关闭时等待模型导致排空顺序不当。它们不改变人格认人、记忆取舍、社交对象、资料内容、回应、成长或睡眠的自主判断。

本轮不重启DSH，不访问或修改正式记忆正文，不调用生产模型，不进行QQ或其它社交平台实测。隔离复现与源码修复不能证明这些问题就是此前DSH desktop Host约60秒启动超时的原因；那次Host启动故障仍保留独立诊断范围。0.13.4的真实登录与待扫码记录见[历史恢复说明](qq-login-recovery.md)。

## 记忆编号重复时不再猜选或扩大删除

同一个人格的不同人物分区可以合法保存同名编号。例如Alice与Bob各有一条`same`记忆，文字搜索原本能分清主体，但仅按裸ID打开详情会取第一条；原遗忘收据只使用裸ID，也可能把另一人物的独立条目一并删除。

列表、搜索、时间线和详情现在提供只读`recordKey`，它是`[recordType,scope,personId,id]`的JSON四元组，不替换已有原始编号。详情读取支持`getMemoryRecord(id,{recordKey?,personId?,scope?,recordType?})`，管理页把选中记录的身份完整传回；裸ID有多个候选，或筛选后仍有多个原件时，返回`MEMORY_RECORD_AMBIGUOUS`，不取第一条冒充正确结果。完整四元组也不能区分的异常重复原件同样明确拒绝。

遗忘仍使用已有选定人物／范围与具体编号。**当前旧依赖和撤销收据只表示裸ID，碰撞时不能安全表示精准撤销，因此本版在任何写入前拒绝该次操作，保留全部资料。** 检查也覆盖选中来源将影响的派生条目；不会先删一部分再报错。唯一编号的正常人物限定遗忘、来源撤销、缓存清理和防重放继续沿用原机制。

本版没有改写旧`revokedIds`／`sourceRecordIds`，没有新增存储schema，也不强制现存资料全局唯一。`recordKey`解决可唯一定位的读取，不代表已解决所有碰撞数据的精准删除。用户遇到“存在同编号记录”时，含义是技术上未能无歧义执行，本次没有删除，不是人格拒绝忘记。

## 真正发送前复核当前连接与权限

旧任务可能先取得许可，再等待语音、资料或其它异步处理；等待期间，用户可能停止接入、停用人格、切换账号或收回能力。仅检查排队时的状态不足以证明提交时仍可发送。

渠道在最后调用具体驱动前再次核对当前协调器、记忆库、实际账号、连接状态和能力许可。停止、挂起与关闭会使等待中的旧任务失效；旧任务不能借新实例、新账号或后来重新启用的连接继续发送。此处执行的是用户已有接入授权，不增加人格必须回复、固定社交对象、逐次批准、频率或内容规则。

调用尚未进入驱动时，可以阻止过期任务继续提交。已经进入外部驱动或平台接受的消息，不保证能够取消或撤回；如实际回执未知，保留未知状态，不伪称未发送或自动重发。完整平台能力仍受[账号能力表](account-capabilities.md)中的真实范围约束。

## 先取消模型，再排空已接纳写入，最后释放写锁

运行时公开`beginClose()`作为同步关闭起点：立即标记正在关闭、清理调度并中止模型工作，阻止启动新的模型调用。适配层先调用它，再等待已接纳的来信、操作命令和持久回执排空，最后完成运行时／仓库关闭并释放writer锁。

这使关闭能够先通知正在生成的模型取消，同时避免过早关掉仓库让已接纳的写入失去保存机会。模型端口需要响应`AbortSignal`；如果外部调用忽略取消且永不返回，本补丁不能保证它有界结束。`beginClose()`本身不删除资料、不释放writer，也不启动新模型；正常`close()`仍完成最终排空和资源释放。它是生命周期顺序，不是让人格睡眠、限制整理频率或清空待办。
