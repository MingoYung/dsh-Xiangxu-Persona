## 0.9.0 instance lifecycle and text-only clearing

adapters/dsh/instances.js owns serialized create/load/select/unload/archive/restore and explicit clear operations. instance-lifecycle.js owns path/allowlist checks, bounded scans, preview fingerprints, maintenance exclusion and the external hashed session ownership store. Owner actions and types are authoritative in [schema section 21](plan/persona/persona-schema.md#21-人格实例生命周期与文本清除090) and [API surface](plan/persona/api-surface.md#090-人格实例管理接口); they add no personality tool or personality judgment rule.

instances.create accepts name and optional autoLoad and assigns a new independent UUID directory. Archive stops and retains data; it is not a separate backup. Restore accepts an archived record, with activate:true required to load. Clearing/partial/cleared records cannot load or restore. Archive, normal switch and cancel never imply clearing or social logout. Attachment is tracked independently and pinned to its original coordinator/item. Stop drains channels through onStopping first, closes that coordinator to new attachments, waits for registered attachment work, then closes it; attachments do not queue behind a lifecycle operation that is itself waiting for a channel to drain. Closed attachment gates refuse new work, and late work cannot attach to a different instance.

clearPreview returns the actual scope/excluded/file and byte totals, exact requiresName, confirmationToken, a 64-lowercase-hex SHA256 version and expiresAt. Its token lasts five minutes, is process-local and bounded to eight previews. instances.clear accepts instanceId, confirmationToken and exact typedName, not arbitrary caller paths or a caller-supplied file list. It checks registry and file state before stopping; a changed post-stop fingerprint yields INSTANCE_CLEAR_STALE with zero deletions and remains stopped until explicit action. Once deletion starts, later errors may leave partial data; only a final scan proving no managed files yields cleared. Partial or recovered clearing states stay unloaded and require a fresh preview and explicit confirmation to continue.

Only allowlisted text, indexes and receipts in the selected root are removed. External task originals, media binaries, shared connection credentials and permissions, DSH session history, external backups, registry and content-free session ownership tombstones remain. Unknown files/links/root overlap block rather than expand the deletion scope. No implicit backup, automatic recreation, old-root reuse or automatic switch follows a clear.

Clear confirmation fixes the exact managed-text list and contents, registry and target state, rather than a hash of every file in the whole directory. The external xiangxu-session-owners/1 stores SHA256(sessionId) to instanceId, preserving old-session attribution after a root is cleared without saving dialogue there. Ownership capture rereads and merges under its exclusive lock; valid external additions are retained and do not invalidate the preview, while conflicts or capacity/lock failures reject before deletion. Limits are 16 non-cleared records plus 256 cleared tombstones, 256KiB registry and 2MiB ownership; list returns all non-cleared plus the last 20 cleared in registry order and explicit completeness. Scan limits are 20000 files and 256MiB; existing core capacity limits still apply. Final 0.9.0 acceptance is centrally maintained in [the acceptance section](management-ui.md#090-final-acceptance).

## 0.11.0 managed personal QQ connection

The DSH adapter may prepare a pinned official NapCat Shell in its own directory, start the existing compatible QQ, expose the real QR flow through owner-only qqBridgeSetup actions, then, after owner confirmation, connect the independent QQ account to the current loaded persona in the default autonomous-social mode (both allowedPrivateIds and allowedGroupIds are ['*']). Individually selected scopes remain an optional privacy/test mode; the persona chooses contacts, whether to attempt friend requests and whether to reply. Incoming friend-request approval has an upstream action but is not yet wired into this plugin; proactive friend requests have no verified public action and the native candidates still need an adapter. Neither gap is a personality prohibition. Official QQ Bot and existing OneBot setup remain secondary paths. Installation, online readiness, inbound acceptance, personality choice, platform acknowledgement and client receipt are separate facts.

NapCat HTTP callbacks use a dedicated recoverable HMAC secret and the original bounded JSON bytes; the former Bearer path remains supported. These secrets and native process ownership do not belong to core or model prompts. Recovery cannot change the instance/root/account/scope or download silently; a manual stop clears its resume intent. No stop claim is made without owned-process evidence. Full user steps and pending/current acceptance are maintained in [QQ setup](qq-one-click-setup.md#0110-final-acceptance); old evidence is not promoted.
