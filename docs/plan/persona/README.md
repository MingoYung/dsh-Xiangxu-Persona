## 一、当前有效设计

这是同一个会积累经历、形成主观印象和性格的人格。它可以在不同人和情境中表现不同，也可以有优缺点。人格自己决定认谁、注意谁、记什么、回不回、等多久、翻不翻记忆、何时主动、何时睡以及如何理解承诺和边界。工程层正确采集环境、保存归属、执行决定、控制资源和恢复失败。

- 人物分区不是多租户权限制度。允许带真实主体地回忆和谈论其他人；避免把A的事误记成B的事。
- 长期记忆有限，琐碎原文可忘，重要概括可以延续。完整过程临时给梳理参考，原件缓存或可回查引用均需如实说明，已消费提交后回收。
- `sleep` 是默认的睡眠整理使用方式；人格仍需选择本次整理工作。`on_write` 合并呈现写入后的整理机会，复用正常对话让人格判断是否必要，不再每写一条自动发起付费整理。`consolidationPlan.run` 是一次性所选增量，`defer` 暂缓；清醒时也可整理。两模式沿用来源和提交游标，不重放旧经历。
- 作息参考不成为固定规定。物理容量临界执行有界缓存与缺口报告，不强迫人格睡觉，不把“没睡”变成拒绝聊天。
- 主动聊天没有每日次数、最小间隔或沉默退避闸门；人格决定下次判断时间或等待的事件。选定时间到了即便无新消息也会再判断；明确的事件型倾听可以一直等到选定事件。
- 承诺和边界是关系/性格判断材料，没有独立履约器、禁忌拦截器或输出审查器。主观印象没有固定证据门槛，主动对话不按来源降权。
- 保留底层正确性：源事件去重、归属不串、请求独立快照、梳理批次提交、只回收已消费热区、睡醒与重启恢复、实际交付确认、明确纠正/遗忘不复活。

## 四、阅读与施工顺序

1. 主计划：先理解人格与工程的决定边界，以及用户需要的完整功能。
2. `persona-schema.md` 与 `architecture.md`：按同一字段、配置、工具和执行链施工。
3. `relation-model.md`、`gaps.md` 与 `api-surface.md`：核人物关联、故障闭环和接入待测。
4. `feasibility.md` 与证据资料：需要核依据时再读；论文结果不直接变行为限制。
5. `self-check.md`：看本次文档检查覆盖及哪些项目还须真实运行。

四阶段只是全部功能的施工先后，不划分产品档次，也不以先跑通一部分代替后半功能。P0先验证宿主能忠实执行人格控制决定；P1接记忆与关系；P2接人格、两模式整理和睡醒；P3接主动及全功能组合回归。

## 五、仍须实测的事项

- 宿主事件与源ID、监听及请求作用域、控制工具、inbox启动和实际交付、完整trace读取、睡眠与重启的端到端行为。
- 字符/字节/token三种资源口径、不同模型路由的缓存和历史注入累积、正常聊天与后台整理竞争时的延迟和费用。
- 描述式人格、印象和默契是否带来用户期待的连续性与情境差异；容量参数是否合适。没有三天长满签名、固定行为预测率、永久正确印象等资格要求。

没有真实运行结果前，不把以上待测写成“已完成”。文档统计与本批核验只在 `self-check.md` 维护，避免四处写行数和过期完成率。
