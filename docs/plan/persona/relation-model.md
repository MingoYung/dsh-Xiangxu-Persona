# 「人」大类：同一人格的不同关系、环境与记忆

> 当前产品入口（0.4.0）：产品名`dsh-Xiangxu-Persona`，包名`dsh-xiangxu-persona`，预设展示名“相续人格”；内部presetId `persona-memory`与数据契约`persona-memory/3`保留兼容。原生设置现为七页，增加QQ/微信兼容桥的普通私聊/群聊与Windows本机声音入口；真实使用仍需用户已有桥和账号。当前实现及证据见[管理界面与验收](../../management-ui.md)与[渠道接入](../../channel-integration.md)。研究和旧版本数字保留各自历史范围，不提升为本版验收。

同一个AI可以因不同对象、场合和经历，形成不同的亲疏、默契和态度。认识A的经历也会改变它的共同性格，进而影响它面对B的方式。这里的分区用于记清“谁说过什么、我怎么理解他、我们发生过什么”，不把每段关系变成密闭租户，也不要求面对所有人表现完全相同。

字段与枚举以`persona-schema.md`的`schemaVersion:"persona-memory/3"`为唯一权威。本文件解释关系数据如何被生产、使用、改变和忘记，不另建一套字段表或按文件数量验收。

## 1. 九个逻辑分区与实际存储

| 分区 | 回答的问题 | 主要数据与实际位置 |
|---|---|---|
| P0 身份与识别线索 | 我认为这是谁，依据是什么？ | `IdentityDocument`；`identity.json`，结合`registry.json`中的环境路由与assignment |
| P1 印象 | 我觉得他怎样，和他相处时我通常怎样？ | `ImpressionDocument`；`impression.json`，可含描述、签名、坐标及关系经历 |
| P2 对象记忆索引 | 什么线索能让我找回与他有关的事？ | `MemoryItem`；`index.json`，四类统一为fact/preference/decision/pattern |
| P3 近期视图 | 这次可能用到哪些最近的原话？ | `RecentEntry`；`shortterm.jsonl`，优先保留引用，按需读取正文 |
| P4 默契编码 | 我和他之间哪些反复出现的含义值得用短标记找回？ | `CodeRecord`；`codes.json`，保留meaning、来源和可用细节入口 |
| P5 相处状态 | 什么时候见过、目前有哪些待接收的话？ | `PersonState`；`state.json`，客观时间与待处理消息，加自由的关系描述 |
| P6 暂时解释 | 我还在怎么理解这件事，想继续观察什么？ | `InterpretationRecord`；`pending.json`，可参与人格判断，不是禁用池 |
| P7 承诺材料 | 谁说过要做什么，后来发生了什么？ | P1 `events[]`中的`RelationEvent.type:"commitment"`，不单设到期强制执行器 |
| P8 边界材料 | 对方表达过什么意愿，我目前怎样理解？ | C3 `facets[]`中的`BoundaryFacet`，通过scope/personId说明共同或专属用途 |

五个存储职责为C1原始聊天、C2检索派生、C3共同人格、C4运行态、C5诊断；H1另作临时完整过程工作区。它们与P0–P8不是可相加的物理文件清单。以下为实际实现建议布局，允许在不改变字段和恢复语义的前提下合并文件，但不得漏掉真正保存原始流与热区的位置：

```text
persona/
├── config.json                       # PersonaConfig
├── registry.json                     # RouteBinding / AssignmentRecord索引
├── self/
│   ├── persona.json                  # PersonaDocument，含P8
│   └── history/                      # 有界人格旧版本，可回退
├── global/
│   ├── index.json                    # scope:global的共同检索材料
│   ├── codes.json                    # scope:global的共同编码
│   ├── state.json                    # RuntimeState
│   ├── snapshots.jsonl               # RequestSnapshot，滚动有界
│   ├── outbox.jsonl                  # OutboxRecord与交付状态
│   └── revocations.jsonl             # 明确纠正/遗忘记录，支持checkpoint压缩
├── journal/
│   ├── intake.jsonl                  # 有界接收元数据、稳定eventId、源游标
│   └── runs/                         # 未提交run与近期manifest，有界清理
├── staging/
│   ├── events.jsonl                  # personId:null的已接收消息
│   └── hot.jsonl                     # 未归属的临时过程/原件引用
└── people/<personId>/
    ├── identity.json                 # P0
    ├── impression.json               # P1与P7
    ├── index.json                    # P2
    ├── shortterm.jsonl               # P3
    ├── codes.json                    # P4
    ├── state.json                    # P5
    ├── pending.json                  # P6
```

`Document<T>`用于有版本的条目集合：对象index/codes/pending分别装`MemoryItem`、`CodeRecord`、`InterpretationRecord`；身份、印象、人格和运行态用其专门文档结构。JSONL每行遵循其记录类型。`personId`在对象文件及每条对象记录中都必填，不能一处按目录隐含、一处又断言行级字段存在。

## 2. 从环境认识人，而不是从会话认证人

宿主会话标识定位一条技术通道，不能直接证明对面是谁。处理顺序是：采集真实可用的环境线索，交人格结合已有关系判断，再把判断转为稳定内部`personId`的存储路由。已确认的路由能作为下次判断的线索，不是永不变的认证结论。

环境来自平台、房间/场合、显示名、发言者标识、头像、时间等适配器可见事实。原生视觉、摄像头、头像匹配只留`EnvironmentSnapshot.visual`适配接口；只有适配器实际可用时才提供观察，不声称任何模型已经能用。

消息属于谁与消息是什么来源也要分开：宿主的`role:user`或`user/message`不等于真人发言，可能混入运行上下文、旧agent指令、插件状态卡或代理自动消息。适配器按真实源kind及content块分类，C1只记录实际参与者对话正文，自动材料按需要进入临时过程或诊断，不能认作“这个人告诉过我”。P0必须用实际样例核出映射，不能仅靠role猜。

认识不清时可以先听、询问或继续观察，均由人格决定。事件先以`personId:null`进`staging/events.jsonl`，避免为维持固定流程而硬认成熟人、硬建新人或强迫用户认证。后续认出后追加`AssignmentRecord`，指回同一根来源并投影到对象视图，不重复计算一次经历。若后来发现认错，同样用新的assignment说明改判和前序记录，纠正投影与相应关系描述；原始发言不变成两次发生。

群聊中房间对应`channelId/sessionId`等环境信息，发言者可有各自`personId/speakerId`。对谁说话与记录是谁说的分开。陌生场合观察谁、是否接话、等谁继续、直接回答哪个对象，进入`attention/replyPlan`，由人格决定，程序只保证没有发错实际目标或把不同说话人合成一人。不会“所有收到的话都必须立即回答”，也不把固定3秒作为人格判断的资格。

## 3. 每个分区怎样变化

**P0** 保存名字、别名、环境线索和可能的外部标识。名字可能变、判断可能错，允许依据新线索修订；未知项可空。记下是对方自述、观察到还是人格解释，不把一条身份线索自动升级为不可更改的硬事实。

**P1** 是主观印象，不是给对方做能力或道德认证。可以从第一次相遇就有“觉得他有些紧张”“和他讲话容易放松”的描述，也可以不确定、矛盾或偏见；之后在梳理中逐渐改变。描述、关系签名、可选坐标只是组织方式，不要求固定两坐标/三阶段才能存在，更不按沉默天数自动扣温度。数值如使用，也只是内部说明，不替人格决定亲疏。

**P2** 的索引为找回材料服务。原话片段可以本地建立轻量入口，完整含义、重要程度和关系解释交人格在正常判断或梳理中形成。`epistemic`说明来源性质，`aboutPersonIds`说明真正谈的是谁。相同问题在不同对象下可有不同的专属答案，但允许明确指向别人的查询。不要把“提到了A”强改成“这是B的经历”。

**P3** 是有限近期视图。初始读取目标约10万字、三天近期优先；不是三天内无论多大都100%必留，也不是把10万字全部送入模型。用户的原意是在太多时按人格组成保留重要内容。已有记忆可从第一轮起被使用，不设20轮禁检索；本轮要不要读、读哪些，由人格决定，程序执行分页和实际token预算。

**P4** 保存只有这段关系才容易理解的短标记，也可以把值得延续的表达发展为共同习惯。`occurrences`提供去重后的实际次数，但一次有意义的经历也能形成编码，不要求先命中5次。`meaning`是直接可读的语义，细节指针只是加速；自然忘掉一些原话不等于双方的默契必须消失。

**P5** 记录最后见面、实际交付时间、已接收待处理事件和自由的关系状态描述。时间流逝本身是新事实，给人格判断“多久没见”。程序不按固定半衰期把关系降成cooling/dormant，不据此自动降频或禁用印象。久别重逢时，人格可以根据旧印象和新的环境线索重新理解熟悉感。

当前有效attention、带目标的replyPlan、retrievePlan及复查/睡眠条件统一保存在`global/state.json`的`RuntimeState.currentDecision`完整快照，重启据此恢复；P5的pendingEventIds只保存待处理源事件，不能冒充完整回复决定。

**P6** 放暂时的解释和问题，方便下次思考：“他刚才可能只是忙，不一定是不想聊。”它可以直接参与判断，不必等3条独立证据或0.6置信才能成为印象。`pending`只是存储名，不意味着被关押。梳理可保留、合并、修改或忘掉，不设固定14天过期。

**P7** 把承诺当成关系经历。比如“说过下次一起看某件事”，可以记提到的时间和后来是否做过；是否现在提起、要不要解释、当时是不是客套，由人格理解。没有到期必提醒、过期必追问、下一次主动必须优先履约的程序SLA。事件状态变化在正常判断或梳理中记录，不能仅因某话题再次出现就机械认定已完成。

**P8** 把对方表达的意愿以及人格的理解存成边界材料。`kind:"boundary"`区分记录类别，`policy`取preference/ask_first/avoid表达目前倾向；作用域说明与谁有关。原话与猜测通过`epistemic`区别，都可交人格理解。它可能选择询问、回避或在新环境中重新理解，不做每轮全量扫描、never_mention硬禁止或生成后的话题拦截。承诺和边界在用户要求下属于人格与关系判断，合并文件不是换个位置继续执行硬规则。

人格的共同`anchor/axes/facets/signatures/habits`在梳理中缓慢演变，既能保留原来的基调，也可因为经历改变。锚并非永不变的宪法；保留有限旧版本能回退。日常体验可以进入P6或关系事件，梳理再整合进较稳定的描述，不要求“3天必须长出12–18条签名”。

## 4. 主动聊天、反馈、等待与睡眠

主动消息按实际发生记录`origin:"ai_initiated"`和`proactiveId`。用户回应、明确拒绝或尚未观察到回复，都是新经历；能明确对应时保存`reactionTo`，不能为了结算强把下一句无关发言算成回应。

同一根事件的重试、转存和多次梳理不得重复累计；随后新的真实回应可以自然巩固性格与习惯。用户接话可能让它觉得“这个话题聊得来”，但这不自动把它原先猜的“对方喜欢X”改标成对方亲口说过。记录不等于事实认证，也不要求所有主观感受接受事实审查。未回复不自动降检索权重、不自动降低重要度、不按固定次数判定打扰；事实交下次人格判断。

日常不设主动次数、最小间隔、沉默退避或固定10分钟扫描闸门。人格通过`persona_decide`表达注意对象、回复/等待/倾听、是否检索、下一次判断、是否睡觉和怎样醒来。它可设置`nextCheckAt/replyAt/wakeAt`，也可用`recheckOn`只等待新消息、环境变化或明确唤醒；睡眠可选择按时间、整理完成后或明确唤醒而结束。调度器执行实际选择的时间与信号，不强迫墙钟计划。人格自己选的复查时间到了要重新判断，不因没有新消息忽略它；选择监听时则保留监听。用户停止主动时执行急停并取消尚未交付的主动队列，这属于落实用户意图。

睡觉时间与时长由人格结合共同性格、关系、现实时间和积压自己决定。正常作息、疲倦和资源后果可以作为参考，不做默认作息强制、三天没睡强制或容量阈值强制睡眠。物理空间不足走资源降级，不能伪装成“它自己决定睡了”。

睡中不输出assistant消息。已选择观察范围里收到的话照常去重记录和排队，是否已读/来源发生时间保留；醒来按对象与通道汇总一次接收，再由人格决定怎么回应。不同对象的消息不混成一次单人发言，睡中消息也不能因“没有回复”而不入记录。

## 5. 两种整理模式、来源与容量

`consolidationMode:"sleep"`为默认：人格自主选择何时睡及是否进行对应增量整理，可以只休息，也可以清醒时显式run；`"on_write"`为用户可选模式：写入后合并机会事实，在正常人格轮由它选择run/defer，不是每次写入自动调用模型。启用或切换前说明后台调用、响应影响与材料碎片化的差异。两种模式共用稳定来源、游标和提交机制，切换不重复消费，不在每次写入后重洗整个库，也不因改模式自动把人格置为睡眠。

长期记忆与本次完整上下文分开：有限`stream.jsonl`留下值得留的聊天原文，索引/印象/编码保留重要提炼；热区留本次整理可用的完整对话、reasoning与工具过程，按缓存和宿主原件指针分页提供。只存一行摘要时，不能宣称已保留完整上下文。宿主无法提供的原件如实标不可用。

梳理使用`ConsolidationRun`固定`runId/inputEndEventId/inputVersions`，生成并校验patch，通过manifest提交后才推进游标。只清除本批成功消费的热区前缀；失败保留供恢复，处理中新增的内容留下一批。未知事件后来被assignment归入对象，也以新接收事件进入相应批次，不漏掉迟到归属。

初始长期目标约100万字是**整个实例**的原文、印象、编码、人格等持久记忆文本总量；不按人各分100万再无限增加。临时缓存约20万字同样按实例计算，近期视图约10万字服务当前对象读取。数量是工程起点，类型条目上限限制存储和注入长度，不能当成印象是否真实或人格是否成立的资格。

自然裁剪时，重要概括与编码可以继续存在，来源保留有界摘要并标原件可用性，不要求永久保存所有原话才能记住意义。明确纠正/遗忘则按`RevocationRecord`更新指定条目及必要派生，重建和回滚不能恢复被明确撤销的内容；这与自然忘掉琐碎细节是不同路径。诊断、备份、journal和retired也要有界，不新增永久审计库。

达到真实安全容量时，可暂停插件冗余复制，保留可用宿主源的有界指针、回补游标并报告`MemoryGap`。正常聊天继续可用，不强迫睡觉。源已不可读时诚实说明缺口，不把有限存储写成永久无损。数据执行锁和人格睡眠是两个状态，不因后台写文件就把它当睡着。

## 6. 来源研究的用途与实现验收

相关研究与开源结构仍可参考，但不直接升级为人格规则：

| 资料 | 可参考的部分 | 不能从中推出的产品规则 |
|---|---|---|
| `research-persona.md`中的CAPS、Whole Trait Theory、关系自我材料 | 关注情境、变异、同一人在不同关系中的表现；原报告注明阅读深度 | 禁用所有场景词、签名必须24条、一次观察不能形成印象 |
| `research-relation.md`的PersonaMem、memobase与关系研究 | 画像组织、时序材料、检索与重新联系的设计线索；按原证据日期与版本解读 | 把人固定为几种分数、沉默90天亲密度减半、前20轮不准回忆 |
| `external-research.md`的记忆、巩固与主动性材料 | 索引、增量整理、时间判断、来源跟踪的工程参考 | F1等于准确率天花板、每天只能主动3次、性格必须客观无偏 |
| 多租户隔离论文与框架文档 | 在真正要求租户隔离时研究对应技术风险 | 本产品所有关系都必须密闭、共同人格受别人影响就是泄漏 |

本文件未重做外网调研。上述出处、日期、阅读层级和未核限制保留在对应研究文件；字段结构和容量是当前项目设计，需要实现测试，不以引用论文代替用户要求。

关系验收侧重执行是否忠实：同一人在不同环境能留下可修订识别依据；未知事件可后来归属；对A的事不误记为B；明确跨对象查询返回真实主体；共同人格可受多段关系影响；首次相处即可形成主观印象；承诺与边界不触发外部硬规则；主动回应事实能交梳理解释；自然淘汰保留重要概括；睡眠期间消息不丢、醒来按对象接收；两模式切换、重启和提交恢复不重复经历。印象是否永远正确、每次主动是否受欢迎、所有承诺是否按时兑现，不作为软件正确性的硬通过门槛。
