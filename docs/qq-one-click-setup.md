# 把相续接到个人 QQ：准备、扫码与自主社交

适用于 0.13.5及兼容的个人QQ向导。打开 **DSH 设置 → 相续人格 → 连接 → QQ**，默认先走个人 QQ 的 NapCat 向导。你只需要确认使用的人格、亲自扫码，并确认将这个独立QQ交给人格自主社交；下载、启动、接口地址和本机密钥由受管连接处理。已有 QQ Bot 官方连接或兼容桥仍可从次级入口使用。

这是把同一个持续人格接到 QQ，不会另造一个“大肥鱼”角色模板。默认自主社交模式授权这个独立QQ的私聊与群聊，不要求你预先选好社交对象。注意谁、联系谁、是否尝试加好友、回不回复、是否主动、记什么、怎样成长及何时休息仍由人格决定。你也可以改用指定对象范围作为可选隐私或测试设置；它控制平台通路，不重写人格。

0.13.5的记忆定位、发送前复核与关闭顺序见[技术补修](0.13.5-technical-safety-fixes.md)，本轮不重启DSH或新增生产QQ实测。0.13.4的QQ登录恢复、相处页状态提示与该轮未测边界见[登录恢复记录](qq-login-recovery.md)。账号功能范围见[能力表](account-capabilities.md)；其中0.12.0及下面的[0.11.0历史验收](#0110-final-acceptance)保留当时证据，不作为本版登录、资料修改或私群往返已通过的证明。

## 第一次连接

1. **先确认当前人格。** 在面板顶部选择并加载你准备使用的人格。已有正式人格可直接接入，不需要新建或清空记忆。不同人格的数据相互独立，切换不会把旧平台会话偷偷改归新实例。
2. **准备个人 QQ。** 在 QQ 页使用一键准备入口。Windows 向导检查已有 QQ 和受管 NapCat，下载并校验固定版本，在独立目录准备运行文件，再启动自己的桥接进程。准备过程显示实际进度和错误；已有可用受管安装会先核实，不反复下载。
3. **出现当前二维码后再用手机 QQ 扫码。** 没有二维码时先按页面区分管理受限、状态未核实和QQ已离线；不是看到waiting_login就要求扫码。页面显示本次真实登录二维码后再确认。扫码确认由你本人完成；“已扫描”“正在登录”“已在线”是不同状态。过期按页面提示刷新同一向导，不把二维码截图或口令发给别人。
4. **核对账号，确认自主社交。** 默认将当前独立QQ的私聊与群聊交给人格自主使用，私聊和群范围都保存为全部（技术值为['*']）。这不表示必须联系每个人或回复所有群消息；联系与回应仍由人格决定。需要缩小接入范围时，可选“指定对象”用于隐私或隔离测试，填写实际QQ号／群号，不能把昵称当作账号标识。
5. **明确接入当前人格。** 确认显示的人格与账号后完成连接。向导会配置自己的 OneBot 操作入口和事件上报，再核实账号在线与通路状态。完成准备或完成扫码都不等于已经完成渠道接入。
6. **发送一条测试消息。** 从当前已接入的私聊或群发来正常消息，核对 DSH 是否收到、归属是否正确，以及 QQ 是否得到真实回复。人格可能决定等待或暂不回复；如果要排查，分别看“是否收到来信”“是否有发送决定”“平台是否确认送达”，不要只凭是否马上回答判断桥坏了。

连接成功后，账号通过后台桥在线，通常不会出现普通QQ聊天窗口。设置页会说明当前人格已经接入，再通过这个账号的私聊或群聊核对实际收发；“已连接”只确认通路状态，完整聊天往返仍需另行验证。添加好友、通话等能力请查看“能力与权限”中的实际支持状态。

接通账号不会自动授予所有平台能力。需要图片、语音、提及、引用等动作时，再查看“能力与权限”中当前驱动的支持、你的许可与实际可用状态。不支持的项目不会因勾选而实现。0.12.0补自己的头像／资料与空间说说，仍需各自实际支持与许可；好友入站处理、群管理、个人QQ文件发送、空间评论读取和实时通话没有因此接通，不能把扫码当作全功能桌面控制。详见[账号能力表](account-capabilities.md)。

## 管理连接受限或QQ离线时

管理口与QQ账号是两层状态：HTTP200里的Unauthorized也会使管理凭据失效，显示60秒本机冷却时只等待本地倒数，再点“重新检查连接”。这不能单独证明QQ退出；界面会保留上次实际核对的账号与时间，旧二维码不作为当前有效二维码。页面隐藏／离开停止UI轮询，错误状态不反复请求认证。

如果新的只读查询明确QQ已离线、loginPhase为offline且没有二维码，后台可证本应用进程归属时提供“重新连接QQ”。本人一次点击重新打开受管登录流程，先确认自己的旧进程树与监听端口已退出，无法证明就报错而不spawn第二套；不按QQ.exe批量结束进程。保存的原人格、账号、接入范围、许可和记忆沿用；普通检查不调用QuickLogin、不刷新二维码。0.13.4只有真正新启动受管QQ时，已保存恢复意愿、当前人格归属与启用桥的账号／API端口均匹配，才向官方NapCat传递唯一的NAPCAT_QUICK_ACCOUNT用于启动快登；它不保证平台接受旧身份，失败仍按当前真实状态扫码。只有新的有效二维码返回才指导手机扫码；已确认但核心未就绪时说明正在完成登录。冷启动owner receipt链仍按[本版验收](account-capabilities.md#0120-current-acceptance)单列。

如果上一次只留下`launching`启动记录，程序还不能核实旧QQ是否属于本次可恢复进程，会显示`NAPCAT_OWNED_LAUNCH_UNVERIFIED`并要求手动关闭旧受管QQ（`manualCloseRequired`）。即使管理页面端口没有监听，也不会再开第二个QQ；记录不会过一段时间就自动失效，程序也不会凭这条未核实记录接管或结束进程。新版真实重连与平台写入是否通过，以本版验收表的实际证据为准。

本次服务刚实际启动的新QQ，最初90秒内如果只是本机管理接口尚未连通，会保持“正在等待本机管理接口就绪”，继续有界检查，不要求重复点击启动，也不提前声称QQ在线或有可用二维码。认证失败、限流或实际业务错误立即显示；已有进程和冷恢复不套这段新启动等待。超过90秒仍未连通会明确显示`NAPCAT_STARTUP_TIMEOUT`，尚未取得登录状态，但没有重复启动QQ；按提示重新检查连接，不另开第二套。

如果仍在等待登录、管理连接已正常核实，且明确显示`NAPCAT_LOGIN_ERROR`，二维码即使因错误被隐藏，也可通过“重新生成二维码”手动取得新码。只有你点击这个按钮才换码，“重新检查连接”和普通状态轮询都不会自动换码。管理认证失败、限流、状态未知、需要重新连接QQ，或手机已确认／正在初始化／已在线时，不提供换码操作；按钮还会核对当前流程，旧页面或旧flow不能更换新流程的码。实际换码成功后后台会重新读取QQ登录状态，不用换码前的旧错误再次遮住新码；本轮真实过期码刷新结果以当前验收记录为准。

## 好友申请与主动加好友

人格可以自主决定认识谁、是否接受好友申请、是否尝试主动添加。连接模式不要求你逐个指定社交对象；程序如实报告已经实现的工具能力，不把缺失接口写成人格行为限制。

**收到好友申请：上游已有能力，当前插件尚未接线。** NapCat v4.18.41 的 set_friend_add_request 可以处理真实收到的申请，使用该条申请上报的 flag 决定同意或拒绝；它不是向指定QQ号发起申请的接口。插件还需要接入申请事件、原始来源与执行结果后，才能把此能力交给人格使用；当前不会把“已扫码”显示成好友管理已经可用。[上游入站申请实现](https://github.com/NapNeko/NapCatQQ/blob/v4.18.41/packages/napcat-onebot/action/user/SetFriendAddRequest.ts)

**主动添加好友：公开OneBot仍缺action，原创原生账号工具已接线。** 0.11.0历史诊断窄范围核对了固定Windows QQ原生契约，并对本人指定目标完成三次受控原生函数调用：旧双参数调用因参数个数抛Error；单对象但混用OneBot UID返回116“账号转换失败”；保留原生查询回调的空UID后返回0“success”。只有最后一次有提交成功回执，用户随后确认收到并通过，实际friend_list也确认好友关系。前两次失败保留，不把三次调用写成三次已发送申请；本轮操作者指定目标的诊断也不能冒称人格自主选人。这个A/B只证明本次目标与参数变化的实际结果，不能推成所有UID域或平台风控的通用解释。用户报告频繁提示后，操作者已停止所有重发；计数规则与冷却时间未知，不加人格频控。生产工具、查询引用、授权和完整档案见[QQ账号操作](qq-account-operations.md)。源码接线不替代正式DSH加载后的工具实测。

## 不需要自己填写哪些东西

个人 QQ 默认向导会处理固定来源下载、版本校验、本机管理地址、OneBot 操作地址、事件回调与随机密钥。WebUI 管理口令、OneBot API 密钥和事件验签密钥分别保管，诊断和页面不回显密钥；不要把整份配置或原始日志贴到公开问题中。

NapCat 在独立目录运行，使用已有兼容 QQ 启动，不替换 QQ 安装包或往 QQ 目录安装 LiteLoader。它会启动并加载到 QQ 进程，QQ 正常运行也会写自己的用户数据；不是直接接管一个已经打开的个人 QQ 窗口。若同一账号还有普通桌面 QQ，会话之间可能相互影响，以实际登录状态为准。向导不以进程名批量结束你的 QQ，也不静默关闭系统安全保护。

当前受管安装入口面向 **Windows x64 与已核实的 QQ 安装**。其它系统、找不到 QQ、不兼容版本或原生启动失败会明确提示，不宣称全平台支持。已有可用兼容桥仍可手动接入。固定 NapCat 版本、校验值和变更依据见[官方发布 v4.18.41](https://github.com/NapNeko/NapCatQQ/releases/tag/v4.18.41)与[官方 Shell 安装说明](https://doc.napneko.icu/guide/boot/Shell)。

## 以后使用与停止

同一人格下，已经由你成功完成接入、渠道仍启用并保存恢复意愿的受管连接，重载后可以核实并恢复。恢复沿用原账号和聊天范围，不重新下载、不扩大范围，也不把其它人格自动接进来。需要重新扫码或在线核验失败时如实提示。

以下是0.12.0阶段历史观察，不是0.13.4当前登录结论：前一阶段正式宿主重新加载后，确实恢复过同一个仍存活的在线受控QQ，未重复启动、无需新QQ扫码。之后一次重启停止了旧受控进程，本次最终运行已新启动受控QQ并取得verified归属证明，目前在二维码页等待本人重新扫码，OneBot API尚不可用。主QQ保持运行且未受影响；不能只凭前阶段在线就判断现在已登录，也不将这些观测合并为优雅关闭或新的私群消息往返已验收，详见[当前阶段记录](account-capabilities.md#0120-stage-observations)。

停止 QQ 接入会停止 DSH 收取这一连接，禁用本应用自己的网络项，并结束能够确认归属的受管启动句柄；它不清除人格记忆。明确停止会取消该受管连接的自动恢复意愿。QQ 进程仍可能继续运行：只有确认退出才能显示已经停止，无法确认时会说明仍需手动关闭，不能把“已停止接入”理解为所有 QQ 进程都已退出。

关闭 QQ 接入、关闭“允许主动找我聊天”、让人格休息、归档人格是不同操作。前者控制平台通路，主动开关控制你是否允许主动联系，休息由人格已有睡眠机制处理，归档保留整个人格的数据。修改连接范围与权限不会重写人格性格。

## 0.13.4：清醒不等于QQ已在线

“相处”页分别显示人格状态与当前QQ连接提示。QQ等待登录时可直接进入连接页；没有取得新鲜确认、上次核验失败与明确离线分别显示，不让你凭“清醒”猜账号是否在线。该提示读取已有状态快照，页面不因此新增后台轮询或模型调用。

2026-10-29的故障定位中，DSH宿主正常，但受管QQ处于等待登录，来信没有进入模型。历史账号快登列表虽有正式账号，一次官方SetQuickLogin返回HTTP200、code:-1，并明确要求重新登录；本次不是快登成功，仍待本人扫码。0.13.4源码补启动快登参数不等于当前已加载或登录成功；最新状态与隔离验证见[本轮恢复记录](qq-login-recovery.md)。

## 页面卡住或没有回复时

| 看到的情况 | 可以怎样处理 |
|---|---|
| 尚未安装／准备中 | 等待明确的准备结果；失败后先看下载、校验或解压错误，不绕过校验执行文件。 |
| 已扫描，仍在登录 | 在手机确认后等待真实在线核验；已扫描不等于 QQ 核心就绪。超过向导等待范围会报告实际状态，不伪装连接成功。 |
| 启动后退出／没有二维码 | 保留脱敏错误，核对 QQ 版本和实际启动情况；不要先清空人格或重装 QQ。 |
| 账号在线，DSH 没收到 | 检查渠道是否启用、接入模式和事件验签状态。自主社交应为全部私聊／群；若改成指定对象，请核对实际QQ号／群号。 |
| DSH 收到了，但 QQ 没回复 | 再区分人格未选择发送、当前能力未许可和平台返回失败／未知；未知回执先查询，不重复发送同一内容。 |
| 停止后 QQ 仍在运行 | 按页面“需要手动关闭”的实际说明处理；插件不全局结束其它 QQ 进程。 |

已知的上游 Windows 报告包含注入崩溃、扫码后未进入在线初始化。它们不证明每台电脑都会失败；兼容表与无登录启动记录也不证明扫码一定成功。向导以本机真实结果判断，不默认重置设备信息、降级 QQ 或关闭安全软件。[官方问题 #2116](https://github.com/NapNeko/NapCatQQ/issues/2116)，[官方问题 #2132](https://github.com/NapNeko/NapCatQQ/issues/2132)

## 其它 QQ 连接方式

- **QQ 官方 Bot：** 单独的官方机器人账号路径，保留原有扫码与平台资质限制，不等于个人 QQ。官方被动回复上下文限制仅作用于这个驱动，不套到 NapCat。
- **使用已有兼容桥：** 自己已经部署 NapCat／OneBot11 时，可填写实际操作 API 与账号。事件上报按桥实际协议选择认证；NapCat 原生 HTTP Client 使用 HMAC-SHA1，不能把它当作 Bearer 回调。受管向导会自动配置这一项。
- **微信、B站与声音：** 保留各自入口和实际能力，不因个人 QQ 一键接入而新增微信普通群、朋友圈或实时通话支持。

技术细节见[渠道接入](channel-integration.md)、[管理界面](management-ui.md)、[字段权威第23节](plan/persona/persona-schema.md#23-个人qq一键准备与受管连接0110)。普通使用不需要逐项研究这些字段。
