# 群聊现场、话语理解与文字交付

2026-11-07 工程候选，继承 E `99fbf354`。本文件说明本次实际采用的结构和验证范围，不把零模型成功写成真实模型语义通过。字段唯一权威为 [persona-schema 第27节](plan/persona/persona-schema.md#27-群聊理解与交付契约2026-11-07候选)。

## 这次解决什么

E 已证明账号、名字观察范围和来源资料进入了模型输入，但真实群里仍把重复的第三人召唤应答成在叫自己。仅继续增加账号资料不能视为解决。当前接入还把群原文放在 `role:user` 的开头，呈现很像二人私聊；是否开口与是否被叫没有独立的实际表达接口。本次改变群现场呈现和最终交付结构，保留同一个人格、同一次生成，不增加另一个判断模型。

新群来信先以带发言者、真实平台消息ID和原文的公开现场呈现，再保留既有 @、引用与观察资料。源 `originalText`、角色和来源仍完整保存。`groupPresentation` 仅标记新投影；旧来信没有该标记时按旧格式重建，不能为了升级重写旧事件。

QQ群最终可见回复使用一个内部 `xiangxu-social` 块。在同一次输出中，人格分别填写对原句对象的理解、自己选择的参与方式和真正要发的话。程序校验结构和容量，只把 `messages` 的正文送到平台。她可以认为对象不确定仍接话，也可以回答叫别人的问题。

2026-11-10 的合并候选 H1 收到了正确的当前群资料，仍生成了无依据的 `addressee:"self"` 和冒领正文。后续候选在交付边界核验明确的 `self` 声明。依据来自本轮唯一一条实际入站并被本会话接纳的来信。有效线索包括实际 @ 本账号、引用带服务端消息 ID 的本账号送达记录，或已记录自称／已核验登录昵称出现在原文句首的直接称呼位置并与 `reference` 一致。同名冲突、输入不完整或匹配截断时，昵称线索不能单独支持 `self`。多条来信之间不互借依据。来源撤销使已准备的证据失效，实际发送前再次核对。线索仍不能独立证明发信人的意图。

随后一次真实 H1 给出 `uncertain`、具体 `reference` 和 `answer`，正文仍以被叫者身份应答。无桥隔离没有送达回执。本地模拟在线桥用原输出复现了旧版确实会派发。当前契约在对象不确定且填写具体称呼时，将 `answer` 定义为以被叫者身份应答，与显式 `self` 一样核本轮证据。缺证据时返回 `SOCIAL_SELF_ADDRESS_UNSUPPORTED`，保留技术回执和待答来信。程序原样保留草稿，不自动重试。作为在场者帮忙或提供线索可选 `join`，也可澄清或等待。

正式 `b46e7a8` 的 Q2 用 `uncertain + join` 送达了以“在——”开头的冒领正文。补修从本轮完整、已接纳且与实际平台发言对齐的原文中识别简单的“具名称呼＋在么”形态，再核验投递气泡开头的独立肯定应声。明确 @、已验证的本账号引用、与原文具名称呼一致的可信自称证据仍可放行。普通群体询问、旁观提供线索、条件式接话和澄清仍可交付。历史送达按旧回执如实重建。此补修只覆盖可稳定识别的问答形态，其余自然语言仍以整轮语义验收，工具主动外发沿用原授权和收据流程。

`61ed9f6` 的真实隔离样本再次自认。模型复述了本轮缺少指向证据，随后用自己以前的应声和对方重复同一称呼来支持自认。组装层现在显式呈现 `currentSelfAddress`，区分尚未观察、当前来源支持和当前来源未解决。近期助手回执标记 `sourceRole: "assistant"` 和 `evidenceScope: "delivery_only"`，用于说明旧应声的来源与送达范围。旧消息原文和角色按原顺序进入会话，相续依然选择自己如何参与。

是否认人、接受新称呼、改自我档案、记住什么、如何成长仍用原有自主接口。`understanding` 不自动改成平台事实、人物绑定或人格名字。原工具、等待、睡眠路径仍可直接选，不要求每轮产生可见回复或先调用 `persona_decide`。

## 实际生产与消费

1. `channels/native.js` 为新群来信添加版本化现场呈现；`normalize.js` 继续取精确原文入库，`completeMessageSource` 按消息自身的投影版本核对完整来源。
2. `index.js` 把同一群聊契约放在本次必要记忆材料之后，附当前注册账号、群、实际发言者和当前观察。`selfAddressEvidence` 只显示本轮已接纳、仍有效的来源，旧回执仍按其真实状态单列。真实 `llm/stream` 边界核验该段存在，其他预设与私聊不进入群契约。
3. 已有 core 辅助 `purpose:reply` 草稿通过 `model.js.replyContext` 取得同一注册群资料；只增补已有调用，不新增规划器调用。增补后用现有计数器和同一输入上限核验，装不下如实报错，不暗中扩大预算或删除来源。
4. 原生 final 带 `outputContract` 进入 `channels/service.js`。`external-output.js` 校验并投影；一次或多条正文沿既有回执、部分发送、语音和去重路径交付。
5. 交流记忆和交付确认使用实际确认的正文。内部块留在宿主原件与过程资料，不能成为说给用户的JSON，也不能自动成为已确认身份。未知或部分结果不自动重发，冷恢复只重建实际已确认部分。
6. 缺格式、坏格式留失败回执和哈希，不发原控制块。下一轮群聊能看到所有近期 final 的交付状态和错误码，包括没有任何 fence 的失败稿；不增加自动收费重试。

## 两个独立的技术修复

普通文本来信现在在外部参考中明确呈现真实 `inputSource.platformMessageId`，不依赖可能被省略的 `environment_details` 或API不会展示给模型的内部 `source` 元数据。`message.read` 缺该ID会在出桥前说明所需参数；`channelId/sessionId` 不能代替平台资源。桥内异步读取的错误经正常 `await/catch` 归类，不再误报成笼统记忆错误。

表情图此前缺字节被误报 `incoming_media_capacity`。托管 NapCat 连接与恢复时启用其官方 `enableLocalFile2Url` Base64 返回选项，按账号保留前像，明确停止时恢复原值并保护外部后改值。已有兼容桥不被擅自改配置；缺字节、不支持和真正容量不足分别报告。没有添加任意本机路径读取、外网下载或提高16MiB容量。

外部来信的可见参考随同一平台消息 ID 提供文字完整性、已观察媒体和引用计数、未被文字覆盖的段类型计数，以及已知的平台源时间。前一条图片的读取状态仍随原件保留，新一条普通文字具有自己的来源。表达参考提醒人格把当下的话、引用和附件与相关旧话题分清，如何接话、继续讨论旧图或提供帮助仍由人格选择。隔离夹具覆盖旧图失败、随后纯文字和明确引用旧图三种输入。

跨午夜真实隔离样本在两项时间戳均正确的情况下误读了日历日和时距。宿主现在从同一请求时钟及该来信的平台源时间计算 `relativeToRequest`。在上海时区 23:58 至次日 00:03 的样本里，投影直接呈现来信属于昨天、距请求五分钟。记录保留实际接收时间供回查。
