# 问题反馈与最小诊断

适用于相续人格0.13.1及后续兼容版本。报错不要求懂代码，也不要求先证明问题一定属于插件。

## 怎样报告

1. 在相续人格设置中打开“报告问题”。设置无法打开时，直接打开[问题申报表单](https://github.com/MingoYung/dsh-Xiangxu-Persona/issues/new?template=bug_report.yml)。
2. 点击“复制最小诊断摘要”或“保存摘要文件”，再检查内容。摘要只在本机生成，不会自动上传，也不会代替你描述问题。
3. 写明“做了什么、实际发生什么、希望发生什么”。能再次出现时按顺序写操作；偶发问题写当时场景和大致时间即可。版本不知道时写“不确定”。
4. 检查后点击页面上方“去 GitHub 报告问题”，在表单里粘贴摘要并主动提交。也可点“复制申报链接”后用浏览器打开。提交后保留Issue链接，后续补充和修复进展都在同一处。

入口打不开或浏览器拦截时，可复制申报链接到浏览器打开。GitHub提交需要GitHub账号；没有账号时，可以先保存最小诊断摘要和复现步骤，通过你已经使用的人工联系渠道转交维护者。本项目不虚构客服邮箱、QQ号或自动工单服务。

## 最小诊断能说明什么

摘要使用白名单生成，只包含取得到的插件包版本、操作系统枚举、架构、Node.js版本、初始化／运行状态枚举和布尔值，以及固定允许错误码的计数。容量不采集，不会为生成诊断扫描记忆或聊天正文。无法可靠取得的项目会说明未提供，不猜测DSH版本或连接是否已经成功。

它不读取聊天正文、人格描述、记忆原文或完整日志，不导出人物／账号标识、会话ID、本机绝对路径、API地址、令牌、Cookie和二维码。不是把原始配置全部导出再简单替换几个敏感键名。用户自行填写的说明和截图仍可能包含私人信息，提交前需要自己检查。

DSH自身的“导出诊断信息”、完整日志或记忆备份范围可能更大，不等同于本插件的最小诊断摘要。不要未经检查就把那些文件放进公开Issue。截图请遮住昵称、账号、头像、私聊、路径、二维码和认证信息。

模型、服务渠道和思考强度只需写名称，不填写密钥、带凭据的URL或账号。如果不涉及模型调用，可以留空。

## 维护者怎样接收

报错表单创建的是本仓库的公开GitHub Issue，默认指派给维护者 `MingoYung`。维护者可在仓库Issues和GitHub通知中接收、分流和补充问题；手机或邮件是否提醒由维护者自己的GitHub通知设置决定。

这不是后台自动上传或持续调用模型的监控。只有用户主动提交，报告才发送到GitHub。摘要提供版本、错误码和技术状态，表单提供实际现象与复现步骤，二者一起帮助定位问题；若信息不足，维护者会在原Issue中请求补充。不要把尚未定位的问题、未完成测试或结果未知标成已经修复。

功能建议和操作不易理解的问题也可以通过[建议表单](https://github.com/MingoYung/dsh-Xiangxu-Persona/issues/new?template=feature_request.yml)反馈。人格自主判断、回忆、成长和表达不由报错通道增加规则。

## 反馈时先保留资料

遇到数据问题时，不要为了复现而清除或重建正式人格。可以先使用已有备份入口保留资料，再描述操作经过。报告问题、生成最小诊断和打开表单不会启动整理、模型调用、扫码、账号操作或删除记忆。
