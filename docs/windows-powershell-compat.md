# Windows PowerShell 启动兼容

相续人格的 DSH 适配层包含一个范围有限的 Windows 启动兼容模块，用于修复部分 Electron 宿主中“PowerShell 工具看似执行结束，却没有执行实际命令”的问题。用户正常安装、重载插件即可使用，不需要为这个故障重装 PowerShell 7，也不需要修改系统或用户级环境变量。

此修复处理进程启动与输入输出，不改变人格如何决定使用工具、委派任务、整理记忆或回复消息。

## 故障表现与原因

受影响的宿主使用 Electron 主程序启动内置的 Windows ACL runner。这个 runner 应当作为 Node.js 脚本执行，再启动受 ACL 约束的 PowerShell 命令。启动链有两个交接问题：

1. 交给 ACL runner 的 Electron 子进程缺少 Node 启动标记，可能按桌面程序路径启动，留下图形缓存相关输出后结束，实际 PowerShell 命令未执行。仅有退出码 0 无法证明成功。
2. 即使补上 Node 标记，Electron 可执行文件仍属于 Windows 的 GUI 子系统。子进程没有可共享的 console 时，原生受限 PowerShell 子进程可能以 `0xC0000142`（`STATUS_DLL_INIT_FAILED`）退出。

本轮在实际打包组件中复现了第二种失败，并验证同时处理两处交接后，PowerShell 能执行标记命令、返回中文输出并遵守原有写入权限。这个故障不等于“没有安装 PowerShell”：本轮验证使用的 PowerShell 7.4.22 本身可以正常直接运行。

补充的真实DSH SDK固定响应联验也通过8项适用检查：实际`pwsh`工具经过安装的兼容wrapper、原`workspace-write`沙箱和原生runner，中文输出与文件字节核对成功，命令和SDK均正常退出。两次provider派发均为本地固定响应，外部真实模型调用为0。实际SDK这条调用没有配置control/FD3，因此本项不声称FD3原生回环覆盖，透传单测仍按其自身范围报告。

## 修复范围与权限

模块只在以下条件全部满足时改写一次子进程启动：

- 当前平台是 Windows，运行时是 Electron。
- 宿主提供原生 `subprocess` 服务和内置 Windows ACL runner 入口。
- 待启动命令的前缀，精确匹配当前 Electron 程序随附的 `resources/app.asar` 内置 ACL runner。
- 该调用尚未自行提供值为 `1` 的 Node 启动标记。

兼容入口为这个子进程临时添加 Node 启动标记。进入 Node 运行时后，它先恢复目标命令原本应有的环境变量，再按需创建并隐藏当前子进程自己的 console，恢复分配 console 时受影响的三个标准输入输出句柄，最后导入并执行原来的 ACL runner。

原 runner 仍然负责 restricted token、ACL 授权与撤销、临时目录及真实命令执行。宿主的 Windows Job 进程管理继续生效。命令参数逐项透传，工作目录、输入输出配置、取消信号、宽限时间和控制字段保留，不增加一层 shell 字符串解析。

模块不会改写父进程的 `process.env`，不会向系统永久设置 `ELECTRON_RUN_AS_NODE`，不会关闭 sandbox，也不会把只读策略改成可写。目标命令原有的环境值、大小写及显式删除项按 Windows 的环境变量合并语义恢复；注入用的 `1` 不应泄漏到目标命令。

console 只在该兼容子进程原本没有 console 时分配，并立即隐藏。已有 console 不作变更；新 console 随所属进程退出而结束。

## 用户怎么使用与排查

这不是一个需要用户选择的“放开权限”开关。插件加载时由适配层安装兼容入口，释放适配层时撤销它。完成安装或更新后，按 DSH 的正常流程重载插件或重启应用即可。

如果仍遇到 PowerShell 无输出、异常退出或工具执行失败，反馈时应包含：

- DSH、插件和 PowerShell 的版本。
- 该工具处于只读还是工作区可写模式。
- 一条不含私人数据的最小复现命令、退出码，以及完整的相关错误摘要。
- 是否有真实命令输出或文件结果，避免只根据退出码 0 判断执行成功。

可使用插件的“报告问题”入口或[仓库问题反馈](https://github.com/MingoYung/dsh-Xiangxu-Persona/issues)。提交公开材料前应移除账号、令牌、个人路径、私人对话和记忆内容。这个兼容模块不需要这些资料，也不要求提交完整日志。

## 上游更新与直通机制

模块按实际服务与可信入口检测适用性，不以固定宿主版本号强行启用。非 Windows、非 Electron、自定义 runner、不匹配的命令、独立 Node runner，以及已经自行提供值为 `1` 的 Node 标记的调用，都保持原样。

每次启动还会重新核对 runner 前缀。宿主改用新的启动契约或不再暴露这个内置入口时，本模块停止改写该调用，交由宿主原流程处理；“停止改写”不代表自动证明新版宿主已经修好。新版兼容性仍需重跑相应验收。

重复安装共用一个 wrapper 并按引用计数释放。释放时不会覆盖其他扩展后来安装的 wrapper；即使后来安装的 wrapper 仍持有旧函数，已释放的兼容入口也会退回原样透传。

## 验收证据与边界

本轮 PowerShell 兼容验证没有调用真实模型，没有运行桌面 CLI，没有启动正式人格或切换正式社交路由，也没有修改已安装应用的 ASAR。各层证据含义如下：

| 层级 | 本轮证据 | 能证明什么 | 不能据此声称什么 |
| --- | --- | --- | --- |
| 函数与安装器单测 | `test/windows-acl-bootstrap.test.js`，12/12 通过 | 同步 live-handle 签名、可信前缀匹配、环境大小写与删除语义、参数及控制配置透传、重复安装与释放、console 处理顺序及失败关闭 | 不能单凭模拟原生 API 证明 Windows 真实命令已执行 |
| 实际打包组件零模型探针 | `scripts/windows-acl-probe.mjs`，使用真实宿主 subprocess、Windows Job、ACL runner 与 PowerShell argv 构造入口 | 实际 PowerShell 执行、工作区写入、UTF-8 输出与文件回读、工作区外写入拒绝、只读拒绝、启动标记未泄漏及显式原值恢复 | 不能冒称完整 Cordis/SDK 应用集成、正式会话或真实模型验收，也未单独验收原生控制 FD 的双向回环 |
| 应用与会话集成 | 需要在隔离宿主中另外执行并登记 | 插件加载、生命周期接线，以及真实工具从会话到子进程的完整消费链 | 本轮组件探针不能代替这一层 |

原生探针使用 Electron 44.7.0、Node 24.21.0、PowerShell 7.4.22。三项实际子进程均选择 `windows-job`，没有接受较弱的进程管理回退：

- 工作区可写模式：命令标记、中文 stdout、UTF-8 文件回读成功，工作区外写入被拒；退出码 0，stderr 为空。
- 只读模式：真实文件写入收到访问拒绝，原文件内容保持不变；有关语言模式和编码前导的限制见下节。
- 显式环境值：目标命令得到原有值，而非兼容入口临时注入的 `1`；退出码 0，stderr 为空。

探针会在独立测试目录保存 `receipt.json`，包括真实观察、失败细节和限制；应读取回执中的 `passed`、实际输出与权限断言，不把发起命令的终端返回当作验收结果。原始回执可能包含测试机路径，不应直接作为公开附件上传。

开发者可先运行 `node --test test/windows-acl-bootstrap.test.js`。原生探针需要在已安装 DSH 的 Electron 可执行文件中，以仅对该探针进程生效的 Node 模式运行；这属于维护者验收流程，不是用户安装步骤。探针限定使用独立测试根目录，不调用模型、不读取账号、不操作正式 profile，也不自动删除失败原件。

## 已知宿主限制：只读模式的语言与编码

实际验证中，只读 ACL 模式下的 PowerShell 处于 `ConstrainedLanguage`。宿主原有 UTF-8 前导使用的 `UTF8Encoding::new(...)` 在这个模式中受到限制，会产生两条类型构造错误，部分含中文的错误路径也会乱码。使用内置 `Set-Content` 的真实写入测试仍收到了访问拒绝，且已有文件内容未变。

“原只读策略不授予临时写入”有宿主源码依据；“出现 `ConstrainedLanguage` 和编码前导错误”有运行证据。二者的具体因果关系未在本轮另做隔离验证，不将合理推断写成已证明的结论。

本兼容模块保留这个限制，不强制切换 `FullLanguage`，不额外授予临时或工作区写权限。只读工具若遇到类型调用受限或编码错误，应按宿主策略问题单独诊断，不能用“关闭沙箱”作为自动回退。

## QQ 验签与 Windows PowerShell 模块路径（2026-11-03）

从 PowerShell 7 启动 DSH 时，Windows PowerShell 5.1 子进程可能继承 7 的 `PSModulePath`。本机实证中，QQ 的签名是有效的腾讯签名，但 5.1 无法自动加载 `Microsoft.PowerShell.Security`，使 `Get-AuthenticodeSignature` 失败，QQ 连接报 `NAPCAT_QQ_SIGNATURE`，尚未启动到扫码阶段。

适配器现在只从本插件 Windows PowerShell 子进程的环境副本移除大小写无关的 `PSModulePath`，由 5.1 初始化自己的默认模块路径。签名检查、QQ 进程归属查询与停止、本地系统语音共用此处理；父进程环境、全局设置、执行策略、签名条件和进程归属规则保持原样。验签仍要求 `Valid` 且签名者为 Tencent；校验失败不会启动 QQ。

只读对照在普通 Node 和 DSH 自带 Electron 的 Node 模式均复现了继承环境失败、局部清理后腾讯验签成功；进程查询的路径、创建时间和 PID 一致。本地受影响测试162/162通过，包含真实 Windows PowerShell 模块加载、无效签名拒绝、原生进程归属与语音边界。这些零模型探针不等于 QQ 收发或真实人格行为验收；正式连接状态另按实际加载回执报告。
